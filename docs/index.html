1. How TensorMMU Maps Computer Architecture to Transformers

In Sparse-MoE models like Qwen3-Next-80B-A3B (512 experts/layer, top-10 active = 1.95% per token) and Gemma-4-26B-A4B (128 experts/layer, top-8 active = 6.25% per token), over 90% of model bytes live in routed expert FFN matrices that are untouched on any single token. Instead of splitting layers across CPU PyTorch threads or failing with CUDA out of memory, TensorMMU compiles every expert into a 4 KB-aligned contiguous UINT4 virtual memory page and manages residency through a 3-tier hardware cache hierarchy:

MMU + Page Table

GPU Slot Table & LRU/LFU TLB

Device-Side Lookup · CUDA Graph Safe

Maps virtual (layer, expert_id) addresses to L1 VRAM slots or L2 Zero-Copy host pointers directly inside fused NVRTC CUDA kernels.

Tier 1 · Hot Cache

L1 GPU HBM / GDDR6X

~1,008 GB/s (RTX 4090) · 3.35 TB/s (H100)

Holds the always-active trunk (embeddings, quantized attention/GDN, shared MLP) plus the hottest K expert pages per layer.

Tier 2 · Warm Cache

L2 Zero-Copy UINT3/4-WINA DDR5

Exact-Byte cuMemHostAlloc · -30% RAM & -50% PCIe

Device-mapped pinned pages with Gate-First conditional neuron fetch (UINT4-WINA / 3-bit UINT3-WINA), expanding 12.7 GiB DDR5 from 137 to 206 experts/layer with zero PyTorch slab waste.

Tier 3 · Backing Store

L3 NVMe Ring + Cold L3 Drop

32-Slot Async DMA · Lookahead · -92% L3 Misses

Unmapped cold misses stream overlapped behind Shared-MLP compute, while CUDA-Graphed hardware-tier pruning skips tiny-weight L3 outliers (slot == -1) with zero syncs.

CUDA-Graphed Native mtp.* + PLD Two-Tier Drafting & Persistent Warm TLB: TensorMMU loads official Hugging Face mtp.* speculative heads in just +190 MiB VRAM (85–92% acceptance, 2.32 tok/step), pairs them with 0.05 ms Prompt Lookup Drafting, and persists warmed L1+L2 expert ranks across restarts in warm_tlb_profile.json so even the first prompt hits 99.7%+ TLB locality.

3. Scientific Honesty, Alternatives & Google / DeepSeek Lineage

Why We Renamed from NeuralVM to TensorMMU (Negative Result Preserved): This project started as NeuralVM to test decompiling dense 31B FFNs into SVD hot trunks + paged cold neuron slices. Because dense SwiGLU layers activate 100% of intermediate channels on every token, paging dense weights either stalls on PCIe bandwidth or degrades reasoning perplexity when cold pages are dropped. Virtual memory requires locality — and native Sparse-MoE routing (1.95%–6.25% active bytes/token) plus token-indexed lookup layers provide exact, lossless sparsity.

Connection to Google & DeepSeek Memory Architectures: TensorMMU complements hardware-aware model designs from DeepSeek's Engram (Conditional Memory via Scalable Lookup, which offloads massive deterministic O(1) N-gram tables to host DRAM over PCIe) and Google's Per-Layer Embeddings (PLE) & Titans (per-layer host-offloadable token lookup tables — supported natively in TensorMMU via ple_host.safetensors — and adaptive neural memory).

How TensorMMU Compares to Alternatives:

  • Strata (Niko1221/Strata), PolyStrata & MoMoE: C++/llama.cpp forks that hit higher peak tok/s (~95–120+ on 64 GB+ RAM rigs) by combining aggressive 2–3 bit (IQ2/IQ3) GGUF quants, native MTP multi-token drafting, and CPU AVX-512 compute for cold experts. TensorMMU instead runs 100% on the GPU at lossless 4-bit directly from Hugging Face .safetensors — paging across VRAM, zero-copy DDR5, and NVMe inside CUDA Graphs (even on 32 GB RAM PCs or CPU-constrained K8s pods) and scaling straight onto AWS H100s.
  • Colibrì (JustVugg/colibri): Pure-C hierarchical NVMe → RAM → GPU MoE engine using raw async C file I/O and .coli_usage hot-store pinning. Colibrì is purpose-built for streaming ultra-giant 400B–744B MoEs (GLM-5, DeepSeek-V3) from NVMe on modest rigs, whereas TensorMMU targets higher single-GPU decode throughput (39–62 tok/s) and full OpenAI/Anthropic tool-calling in the 26B–120B+ regime via L2 Zero-Copy mapped PCIe reads and Full/Piecewise CUDA Graphs.
  • Adaptive KV Streaming (RaymondHuang210129): Orthogonal and complementary — streams long-context KV cache blocks (128K–256K) from System RAM through a shared GPU ring buffer when weights already fit in VRAM, whereas TensorMMU pages MoE model weights while growing a GPU-resident KV cache on demand (4K → 32K).
  • llama.cpp & KTransformers: Execute offloaded MoE experts on host CPU cores (AVX-512 / AMX). Ideal for 8–12 channel DDR5 Xeon/EPYC servers; TensorMMU instead pages/maps cold experts directly into NVIDIA GPU SMs so standard 2-channel DDR5 desktops aren't bottlenecked by CPU compute.
  • Unified-Memory Servers (Halogen Flash Server, MLX): Hit ~37–45+ tok/s when 100% of an 80B MoE fits in 128 GB+ unified memory (Strix Halo / M-Ultra) with no PCIe bus; TensorMMU bridges discrete NVIDIA GPUs across VRAM, DDR5, and NVMe.

4. Built for Autonomous Coding Agents (OpenAI + Anthropic + Tool Calling)

Local coding agents frequently fail not because of model intelligence, but because of subtle server defaults (as documented in Doug's guide on tuning local coding agents):

  • No More Mid-File Tool Call Truncation (`max_tokens = 32,768` + `thinking_token_budget = 6,144`): In both OpenAI and Anthropic protocols, max_tokens caps reasoning + visible text + tool-call JSON combined. With an 8,192 default, a 6,000-token thinking trace leaves ~2,100 tokens — slicing a 300-line write_file tool call in half! TensorMMU defaults max_tokens to 32,768 while enforcing an automatic 6,144-token thinking cap (injecting </think> or <channel|> cleanly when reached so 26,000+ tokens remain for code output).
  • O(1)-Overhead Growable Static KV Cache: Pre-allocating 32,768 KV slots upfront would waste 7.3 GiB of VRAM on short turns. TensorMMU's CUDA-graphed KV pool starts compact (max(4096, prompt + 2048), < 900 MiB) and grows layer-by-layer (4K → 8K → 16K → 32K) only when a turn actually runs long.
  • Native Dual-Protocol Tool Calling: Parses both Qwen3 XML/JSON <tool_call> blocks and Gemma 4's typed <|tool_call>call:fn{...}<tool_call|> syntax into structured OpenAI tool_calls and Anthropic tool_use / input_json_delta SSE events, while automatically normalizing multi-turn tool_result histories.

5. Hardware Safety, Docker, Kubernetes & AWS Scaling

Before downloading or loading a model, tmmu check (and tmmu serve automatically) inspects GPU compute capability (blocking unsupported pre-Ampere GPUs like AWS g4dn Turing T4 sm_75 with a clear diagnostic), free VRAM, Linux cgroup v1/v2 container memory limits, /dev/shm capacity, and free disk space. 

# 1. Check if a model fits your GPU before downloading a single weight shard:
tmmu check Qwen/Qwen3-Next-80B-A3B-Instruct

# 2. Compile & serve locally via Python CLI:
tmmu compile google/gemma-4-26B-A4B-it
tmmu serve --model google/gemma-4-26B-A4B-it --port 8000

# 3. Or launch with Docker — HTTP binds immediately!
#    GET /livez  -> 200 OK
#    GET /readyz -> 503 Service Unavailable (while downloading & stream-compiling) -> 200 OK when ready
#    POST /v1/messages & /v1/chat/completions -> 503 (Retry-After: 10) until ready
docker compose up --build
